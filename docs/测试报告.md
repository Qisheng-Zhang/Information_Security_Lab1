## 2. 测试策略

### 2.1 遇到的核心困难：没有可用的标准测试向量

本作业的 **SBox2 被改写**（作业原文：「此处的 S-box2 与 PPT 上面的相比略有改动，以此处为准」）：

| | SBox1 | SBox2 |
| --- | --- | --- |
| 本作业 | `(1,0,3,2)(3,2,1,0)(0,2,1,3)(3,1,0,2)` | `(0,1,2,3)(2,3,1,0)(3,0,1,2)(2,1,0,3)` |
| 标准 S-DES | 相同（即 S0） | **不同**（标准 S1 为 `(0,1,2,3)(2,0,1,3)(3,0,1,0)(2,1,0,3)`） |

因此公开资料中的标准 S-DES 测试向量不能未经核对就作为本作业的期望密文。项目采用以下检查来核对规格和实现一致性：

| 验证手段 | 作用 |
| --- | --- |
| **① 规范表逐格核对** | 确认 8 张置换表/S 盒的每个数字与作业文档一致 |
| **② 手算比对** | 用教材经典密钥 `1010000010` 核对 P10、K1、K2 等中间量 |
| **③ 双实现交叉验证** | 整数位运算实现 vs 逐位字符串参考实现，独立编码、结果必须一致 |
| **④ 回环自洽 + 雪崩统计** | 6个密钥各遍历256个明文并另抽样20000组回环；统计雪崩均值 |

### 2.2 测试约定

- 每个测试模块暴露 `main() -> int`，全通过返回 0，否则打印失败项并返回 1；
- 断言用 `check(name, condition, detail)` 累积，任何一项失败都会使整体失败；
- 第 3 关测试**完全离线自测**：以 `port=0`（由系统分配空闲端口）在后台线程启动真实服务端，无需人工干预。

## 3. 分关卡测试结果

### 3.1 第 1 关 · 规格表与基本加解密

提交证据：[加密及逐步跟踪](../截图与视频/第1关_加密.png)、[解密](../截图与视频/第1关_解密.png)、[随机输入](../截图与视频/第1关_随机.png)、[算法规格](../截图与视频/算法规格.png)。下面检查表是原报告的历史记录；截图可以直接复核样例输出及规格表。

实现的密钥调度是 `K1=P8(LS1(P10(K)))`、`K2=P8(LS2(LS1(P10(K))))`；`LS1` 和 `LS2` 都分别旋转左右两个5位半部，第二轮相对于P10结果累计左移3位。规格截图的 `Shift^i` 简式应按此递推过程解释。轮函数先计算 `X=EPBox(R)⊕K`，再把X的左右4位送入两个S盒，最后用SPBox重排。

**规格表一致性（14条检查，原报告记录通过）**

| 项目 | 期望值 | 结果 |
| --- | --- | --- |
| `P10` | `(3,5,2,7,4,10,1,9,8,6)` | ✅ |
| `P8` | `(6,3,7,4,8,5,10,9)` | ✅ |
| `IP` | `(2,6,3,1,4,8,5,7)` | ✅ |
| `IP⁻¹` | `(4,1,3,5,7,2,8,6)` | ✅ |

| `SPBox` | `(2,4,3,1)` | ✅ |

| `Shift2` | `(3,4,5,1,2)` ≡ 循环左移 2 位 | ✅ |

**密钥扩展手算核对（7 项断言）**

```
K1 = 10100100     K2 = 01000011
```

这组中间量与经典密钥示例一致，支持该样例的 `P10 / P8 / 循环左移` 核对。边界密钥 `0000000000` 与 `1111111111` 也在历史测试的检查范围内。

| 随机（密钥, 明文）对 | 20000 组 | **0** |

**与外部搭档程序的互验（历史记录；当前提交不含对方源码）**

上述独立第二实现由本人编写，严格来说仍属"自证"。在拿到第二组的真实源代码（`SDES.zip`）后，
项目提供了 `tests/cross_test.py`：把**对方的程序**当作外部实现独立加载（独立命名空间，不碰本项目 `sdes` 包），
对方位表示是 `list[int]`、S 盒命名 `S_BOX_1`/`S_BOX_2`、直接置换叫 `P4`、字符串模式用 latin-1，
与本项目（0/1 字符串、`SBOX1`/`SBOX2`/`SPBOX`、UTF-8）差异很大——脚本内部做了适配层，
比对的正是"输入输出口径"而非代码形态。

需另行提供兼容外部实现后复现：

```powershell

```

`tests.cross_test` 默认寻找 `_组2参考/SDES/sdes`。该目录当前不存在，直接运行默认命令会以“找不到对方的实现目录”退出；`tests.run_all` 不调用该脚本。外部适配器要求约定的加解密、位串转换及规格表接口，不是任意 S-DES 程序都能直接加载。另外，外部密钥调度接口缺失时脚本会跳过该项，可选字符串模块的差异不计入最终退出码，因此不能仅凭退出码 0 宣称所有附加项都已验证。

> `[(0,1,2,3);(2,3,1,0);(3,0,1,2);(2,1,0,3)]`（标准 S-DES 的 S1 并非如此）。
> 双方都遵循了作业那条备注，因此密文才相同。

**跨人/跨平台一致性（支撑第 2 关要求）**

- 算法流程与全部转换单元（P-Box、S-Box）在 `sdes/core.py` 中作为**唯一数据源**，任何人使用本项目都会得到完全相同的表；
- GUI 第 2 关可导出/导入 CSV（列固定为 `pt,key,ct`），随机种子固定为 `20261008`，因此两人各自生成的文件可逐行比对，输出「一致 N/N 行」；
- 项目**零第三方依赖**，仅用 Python 标准库，避免因环境差异导致结果不同。

### 3.3 第 3 关 · ASCII 字符串加密与 TCP Socket 通信

提交证据：[服务端与客户端](../截图与视频/第3关_服务端与客户端.png)、[网页版通信](../截图与视频/第3关_网页版.png)。控制台截图显示4条消息全部往返成功；网页版截图的 `This is a test` 得到密文 `2268C72762C72762BD624EF8274E`，服务端回显与原文一致。

字符串按指定编码转为字节后逐字节加密，默认UTF-8，8位分组无需补位。客户端提交给 `DEC` 的消息载荷是密文；服务端响应仍包含明文，`KEY` 命令也会返回密钥，故演示不是双向全程加密的安全通信协议。

### 3.4 第 4 关 · 暴力破解

`python -m sdes.crack` 的演示入口实际通过 `brute_force_by_key()` 调用默认4线程的 `brute_force_threaded()`；截图中的6.00ms不能标作单线程计时。单线程的4.885ms来自另一个15次取中位数的性能基准。

**破解功能（9条检查，原报告记录通过）**

| 检查项 | 实测结果 |
| --- | --- |
| 单线程破解结果包含真实密钥 | ✅ 3 个候选 |

| 多线程与单线程候选集合一致 | ✅ |

| 两对结果包含真实密钥 | ✅ |
| `workers = 1/2/4/16` 结果全部一致 | ✅ |

> **结论（如实报告）**：线程版本反而略慢。原因是 S-DES 密钥空间仅 1024 个，单线程一次完整穷举约 5 ms 已在毫秒级；而 CPython 的 GIL 使纯 Python 的 `encrypt_int` 无法真正并行，线程只增加分块与合并开销。
> 多线程实现可作为候选集合一致性与线程开销的教学对比。扩展实验的CLI用 `subprocess` 启动进程，效果应以对应环境和实验数据为准。
> 作业原文对多线程的表述为可选建议（「你也可以考虑使用多线程的方式提升破解的效率」），本项目已提供该实现并给出实测数据。

### 3.4.1 第 4 关进阶 · 扩展密钥空间（`sdes/longkey.py`，73 项断言）


**并行：多线程无加速，多进程走 `subprocess`**

历史扩展实验记录 workers=2/4/8 分别为4484/4496/4529 ms，单线程4464 ms，加速比约0.996/0.993/0.986，未观察到提升。对这类纯Python计算，常规带GIL的CPython线程还会引入调度和合并开销。本项目的CLI并行路径使用 `subprocess` 进程。

原开发环境曾记录 `multiprocessing` / `ProcessPoolExecutor` 创建命名管道时失败，报 `PermissionError: [WinError 5]`；这是该次受限环境的记录，不是所有Windows或Python环境的限制。

`crack_subprocess` 因此改为「每个子进程负责一段连续区间 → 结果与进度**写文件** → 父进程读文件求和」，
结果交换使用文件。以下是历史基准（22-bit、30万候选区间），与当前24-bit截图是不同实验：

| 方式 | 耗时 | 加速比 |
| --- | --- | --- |
| 单线程 | 4483.0 ms | — |
| subprocess ×2 | 2556.2 ms | x1.75 |
| subprocess ×4 | 1426.9 ms | x3.14 |
| subprocess ×8 | 1172.2 ms | **x3.82** |

`crack_subprocess` 对进程启动等 `try` 块内异常会回退单线程并返回 `fallback_reason`；它不会捕获所有失败：创建工作目录位于该 `try` 块之前，且父进程未显式检查各子进程退出码。应结合 `tried/span`、候选集合及错误信息判断搜索是否完成。`crack_parallel`（`ProcessPoolExecutor` 版）另保留异常回退路径，原报告记录其曾触发 `PermissionError: [WinError 5]` 回退。

**三个必须区分的概念**

| 概念 | 含义 | 本算法结论 |
| --- | --- | --- |
| 子密钥调度等价 | 两个主密钥生成相同的 `(K1,K2)` | 当前分组方式检查此项；历史记录无重复 |
| 全局函数等价密钥 | 两密钥对**全部256种**明文给出相同密文 | 不能仅由不同子密钥对推出不存在；当前分组方法不足以证明该结论 |
| 特定明文碰撞 | 对**某个给定明文**，多密钥给出相同密文 | **大量存在**（最大桶 12 个） |

- **源码结论的边界**：`equivalent_key_classes()` 只按 `(K1,K2)` 分组，`tests.test_all` 对空分组的行为比较是平凡检查；`tests.test_webapp` 也只是比对该函数返回的计数。1024个不同子密钥对并不自动证明1024个不同完整加密函数。要实证排除全局函数等价，应按各密钥的256项输出向量分组；本次未执行该枚举，不作“无全局等价密钥”的结论。
- **鸽巢原理**：对任意固定明文P，1024个密钥的输出最多有256种密文取值，因此至少有某个密文对应多个密钥。这不表示每一种密文都有多个候选；截图直方图含4096个大小1的非空桶。
- **平均值的分母**：令 `d(P)` 为固定明文P下实际出现的密文数量，程序先求 `1024/d(P)`，再对256个明文平均。界面4.285是这个非空桶口径。截图桶数合计61184，密钥条目加权合计262144，合并非空桶平均为 `262144/61184≈4.285`。若把全部256种密文的空桶也计入，平均为4；若均匀抽取真实明文与真实密钥，实际候选数需按桶大小加权，截图直方图给出 `Σ(桶大小²×桶数)/262144=5.4140625`。这三种抽样口径不能互换。

**对作业问题的回答**：**会**。对任意给定明文分组，至少存在两个不同密钥得到相同密文，图中最大桶有12个密钥。单组明密文对不能保证唯一确定密钥；部分单组对应单候选桶，而第4关提交样例对应3个候选。增加不同明文的约束可收窄候选集合，但两对不保证唯一，历史样例使用两对仍有2个候选。源码文字报告里的“无全局等价”和“约1.016个候选”是过度推论，本报告不把它们当作当前实现已经证明的结果。

## 4. 雪崩效应（算法安全性分析）

雪崩效应衡量「输入变化 1 bit 引起输出平均变化多少 bit」，理想值为分组长度的一半（8 bit 分组 → 理想 4.0 bit）。

| 测试项 | 实测均值 | 理想值 | 评价 |
| --- | --- | --- | --- |
| 明文翻转 1 bit → **密文**变化 | **3.926 bit** | 4.0 | 接近理想，扩散良好 ✅ |
| 密钥翻转 1 bit → **密文**变化（固定明文） | **2.864 bit** | 4.0 | 略低，符合 S-DES 结构 |
| 密钥翻转 1 bit → **子密钥**变化 | **0.800 bit** | — | 扩散很弱（见下） |

**关于子密钥雪崩仅 0.800 bit 的说明**：这是 S-DES **算法本身的固有性质，不是实现缺陷**。原因有两点：

1. `P8` 只从 10 位中选 8 位，丢弃 2 位，因此部分密钥翻转会被完全屏蔽；
2. 密钥左半的循环左移是独立的 5 位旋转，某些比特翻转只影响其中一个子密钥。

实测分布也印证了这一点：全部 1024×10 次单比特翻转中，子密钥差异为 1 bit 或 2 bit，总和平均 1.6 bit（两个子密钥合计），即每子密钥 0.8 bit。这一弱扩散性正是 S-DES 仅作为教学算法、不具备实用安全性的原因之一。

## 5. 结论

1. **测试记录**：原报告记载4个模块通过，当前正常路径为291条检查记录。它包含1024组项目内双实现比对、6个密钥各遍历256个明文的回环，以及20000组随机回环；本次文档整理未重新运行。
2. **第1—3关截图**：[基本加密](../截图与视频/第1关_加密.png)、[CSV交叉比对](../截图与视频/第2关_交叉测试.png)、[TCP往返](../截图与视频/第3关_服务端与客户端.png)分别展示样例输出、200/200行一致和4/4条消息往返成功。中文按UTF-8字节处理；网络演示的解密请求发送密文，响应回传明文。
3. **第4关**：[穷举截图](../截图与视频/第4关_穷举.png)显示6.00ms且含真实密钥的3个候选；[性能基准](../截图与视频/第4关_性能基准.png)单线程中位数4.885ms，线程配置均更慢。
4. **第5关**：[封闭测试截图](../截图与视频/第5关_封闭测试.png)显示262144个组合、最大桶12、非空密文桶平均候选约4.285。鸽巢原理保证每个固定明文至少有某个多密钥碰撞；单组不保证唯一，两对也不保证唯一。当前按子密钥对分组的实现不足以证明不存在全局函数等价密钥。
5. **安全性分析**：原报告保留明文雪崩3.926bit与每个子密钥0.800bit的历史统计；这些均值用于描述教学算法，不能单凭接近理想雪崩值证明安全性。
6. **界面范围**：tkinter、网页版与CLI复用同一内核。网页测试的148条正常路径检查覆盖HTTP接口和核心输出比对，不是实际浏览器或桌面GUI的交互自动化测试。
7. **外部互验边界**：原报告保留第二组程序全空间262144组双向互验零失败的历史记录。当前提交缺少对方源码；需通过 `--other` 另行提供兼容实现才能复现，当前截图仅直接支持200行CSV一致。
8. **第4关扩展及视频**：级联版本支持10～40位主密钥，单层仍使用作业版S-DES。[22位截图](../截图与视频/第4关_扩展密钥空间22bit.png)显示1分08秒完整搜索，唯一候选 `1111101010001111111100`；[24位8进程截图](../截图与视频/第4关_并行8进程.png)是部分搜索，速度比约4.59。[视频](../截图与视频/第4关_破解演示.mp4)记录另一轮22位搜索，程序耗时59.0秒，完整遍历并命中真实密钥，但保留6个候选，未唯一确定。
