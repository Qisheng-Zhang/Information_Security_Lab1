## 1. 总体架构

### 1.1 分层设计

项目按「算法内核 → 编码适配 → 应用层」三层组织，层间只允许上层依赖下层：

```
┌──────────────────────────────────────────────────────────────┐
│ 应用层                                                        │
│   sdes/webapp.py   网页版后端（标准库 http.server + JSON API） │
│   sdes/web/        网页版前端（index.html / style.css / app.js）│
│   sdes/gui.py      tkinter 桌面界面（5 个关卡分页）            │
│   sdes/server.py   TCP 服务端（解密、应答）                    │
│   sdes/client.py   TCP 客户端（加密、发送）                    │
├──────────────────────────────────────────────────────────────┤
│ 编码适配层                                                    │
│   sdes/codec.py    ASCII/UTF-8 ↔ bit 串 ↔ hex，字节分组       │
│   sdes/crack.py    暴力破解、密钥碰撞与封闭测试分析            │
│   sdes/longkey.py  扩展密钥空间（级联 S-DES，10~40 bit）      │
├──────────────────────────────────────────────────────────────┤
│ 算法内核层                                                    │
│   sdes/core.py     置换表、密钥调度、S 盒、单分组加解密        │
└──────────────────────────────────────────────────────────────┘
```

依赖关系（均为单向）：

| 模块 | 依赖 |
| --- | --- |
| `sdes/core.py` | 仅标准库 |
| `sdes/codec.py` | `sdes.core` |
| `sdes/crack.py` | `sdes.core`、`threading`、`concurrent.futures` |
| `sdes/longkey.py` | `sdes.core`、`argparse`、`subprocess`（并行破解） |
| `sdes/server.py` | `sdes.core`、`sdes.codec`、`socketserver` |
| `sdes/client.py` | `sdes.codec`、`sdes.server`（复用转义与密钥校验） |
| `sdes/webapp.py` | `sdes.core`、`sdes.codec`、`sdes.crack`、`sdes.client`、`http.server` |
| `sdes/gui.py` | `sdes.core`、`sdes.codec`、`sdes.crack`、`tkinter` |

> 网页版与桌面版是**同一内核的两套皮肤**：两者都不自己实现任何密码学逻辑，全部转发给 `core`/`codec`/`crack`，
> 同一输入应得到相同的算法结果，但输入清洗、编码、CSV 取样和网络回包处理仍由各入口完成，需分别核对。
> 两个界面调用同一内核不构成独立实现的交叉测试；独立比对应使用 `tests/gen_vectors.py` 或外部搭档程序。

### 1.2 关卡与模块对应

| 关卡 | 要求 | 主要实现 |
| --- | --- | --- |
| 第 1 关 基本测试 | GUI 加解密，8-bit 明文 + 10-bit 密钥 → 8-bit 密文 | `sdes/core.py` + `sdes/gui.py` + `sdes/webapp.py` |
| 第 2 关 交叉测试 | 统一算法流程与转换单元，跨人/跨平台结果一致 | `sdes/core.py` + `tests/test_all.py` + `tests/cross_test.py` + 网页版「交叉测试」页 |
| 第 3 关 扩展功能 | ASCII 字符串加密（按 1 Byte 分组）+ TCP Socket 通信 | `sdes/codec.py` + `sdes/server.py` / `sdes/client.py` + `sdes/webapp.py` 的 `/api/tcp/send` |
| 第 4 关 暴力破解 | 由明密文对穷举 10-bit 密钥，比较单线程与多线程耗时 | `sdes/crack.py` + `sdes/gui.py` + `sdes/webapp.py` 的 `/api/crack` |
| 第 4 关 进阶（附加） | 扩展密钥空间，使破解耗时足够录制演示视频 | `sdes/longkey.py`（级联 S-DES） |
| 第 5 关 封闭测试 | 分析是否存在多个密钥得到相同密文 | `sdes/crack.py` 的 `analyze_collisions` / `collision_report` |

### 1.3 位编号约定（全项目统一）

- 所有位置**从 1 开始编号**，最左边一位是位置 1；
- 置换 `P` 的输出第 `i` 位 = 输入的第 `P[i]` 位；
- S 盒查表：**行号 = 输入第 1、4 位**，**列号 = 输入第 2、3 位**（均为 2 进制转 10 进制）。

> ⚠️ **规范差异（全项目最重要的约束）**：本作业的 SBox2 与标准 S-DES（Schaefer, 1996）的 S1 不同。
> 作业原文备注：「此处的 S-box2 与 PPT 上面的相比略有改动，以此处为准。」
> 因此公开标准向量不能直接作为本作业的期望密文，应结合规格表核对、手算中间量、回环与独立实现比对判断正确性。

## 2. 算法内核：`sdes/core.py`

### 2.1 规范常量

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `P10` | `(3,5,2,7,4,10,1,9,8,6)` | 密钥初始置换 |
| `P8` | `(6,3,7,4,8,5,10,9)` | 子密钥压缩置换（10 → 8 bit） |
| `IP` | `(2,6,3,1,4,8,5,7)` | 初始置换 |
| `IP_INV` | `(4,1,3,5,7,2,8,6)` | 逆初始置换 |
| `EP` | `(4,1,2,3,2,3,4,1)` | 轮函数扩展置换（4 → 8 bit） |
| `SPBOX` | `(2,4,3,1)` | S 盒输出置换（即 P4） |
| `SBOX1` | `((1,0,3,2),(3,2,1,0),(0,2,1,3),(3,1,0,2))` | S 盒 1（与标准 S0 相同） |
| `SBOX2` | `((0,1,2,3),(2,3,1,0),(3,0,1,2),(2,1,0,3))` | S 盒 2（**与标准 S1 不同**） |
| `SHIFT_1` / `SHIFT_2` | `1` / `2` | 左右两个 5 bit 半部的循环左移步长，第二步在第一步结果上继续移位 |
| `BLOCK_BITS` | `8` | 分组长度 |
| `KEY_BITS` | `10` | 密钥长度 |

### 2.2 算法公式

```
密钥扩展:  X  = P10(K)，分为两个 5 bit 半部
           X1 = LS-1(X)，K1 = P8(X1)
           X2 = LS-2(X1)，K2 = P8(X2)
加密:      C   = IP⁻¹( f_K2( SW( f_K1( IP(P) ) ) ) )
解密:      P   = IP⁻¹( f_K1( SW( f_K2( IP(C) ) ) ) )
轮函数:    f_K(L, R) = ( L ⊕ F(R, K),  R )
           F(R, K)  = SPBOX( SBox1(EP(R)⊕K 的高 4 位) ‖ SBox2(EP(R)⊕K 的低 4 位) )
```

`LS-n` 分别循环左移左右两个半部。因此 K2 相对 P10 输出累计左移 3 位；网页规格页的 `Shift^i` 简写应按这一步序列解释，不能理解为直接对 P10 输出仅左移 2 位。

### 2.3 内部工具函数

| 函数 | 签名 | 说明 |
| --- | --- | --- |
| `bits_to_int` | `(bits: str) -> int` | 0/1 字符串转整数，非法字符抛 `ValueError` |
| `int_to_bits` | `(value: int, width: int) -> str` | 整数转定宽 0/1 字符串（左侧补零） |
| `validate_key` | `(key: str) -> int` | 校验并解析 10-bit 密钥，去首尾空白与普通空格；下划线需由调用方先清理 |
| `validate_block` | `(block: str) -> int` | 校验并解析 8-bit 分组 |
| `_permute` | `(value: int, n: int, table: tuple) -> int` | 通用置换：按 `table` 从 `n` 位中取位重组 |
| `_rot_left` | `(value: int, n: int, k: int) -> int` | `n` 位整数循环左移 `k` 位 |
| `_sbox` | `(box: tuple, nibble: int) -> int` | 单个 S 盒查表，`row = b1b4`、`col = b2b3` |
| `_f` | `(block: int, subkey: int) -> int` | 轮函数 `F(R, K)`，返回 4 bit |
| `_fk` | `(block: int, subkey: int) -> int` | 含子密钥的轮变换 `f_K(L,R)` |
| `_swap` | `(block: int) -> int` | 左右各 4 bit 互换（SW） |

### 2.4 公开 API

| 函数 | 签名 | 说明 |
| --- | --- | --- |
| `key_schedule` | `(key) -> tuple` | 返回 `(K1, K2)`，每个 8 bit；`key` 可为 int 或 0/1 字符串 |
| `encrypt_int` | `(plaintext: int, key: int) -> int` | 整数接口加密（批量运算主力，无字符串开销） |
| `decrypt_int` | `(ciphertext: int, key: int) -> int` | 整数接口解密 |
| `encrypt` | `(plaintext: str, key: str) -> str` | 0/1 字符串接口加密 |
| `decrypt` | `(ciphertext: str, key: str) -> str` | 0/1 字符串接口解密 |
| `encrypt_hex` | `(plaintext_hex: str, key_bits: str) -> str` | hex 明文（2 位）→ hex 密文 |
| `decrypt_hex` | `(ciphertext_hex: str, key_bits: str) -> str` | hex 密文 → hex 明文 |
| `trace` | `(plaintext: str, key: str) -> dict` | 返回加密全过程中间量，供手算比对与 GUI 展示 |

`trace()` 返回的字典键（GUI 第 1 关「逐步跟踪」即按此顺序展示）：

```
key, plaintext,
"P10(K)",
"L1|R1 (P10 左5|右5)",
"K1", "K2",
"IP(P)", "L0", "R0",
"F(R0,K1)", "f_K1(IP(P))",
"SW(...)",
"F(L1',K2)", "f_K2(SW(...))",
"IP^-1(...) = C"
```

### 2.5 设计要点

- **双实现互为验证**：`core.py` 内部用整数位运算（性能好，服务于第 4、5 关的全空间穷举）；`tests/test_all.py` 中另有一份逐位字符串参考实现 `_ref_encrypt`，两者在 4 个密钥 × 256 个明文上完全一致。
- **为什么用整数内核**：第 5 关需要 `1024 × 256 = 262144` 次求值，若每次都做字符串拼接与切片，耗时会放大一个数量级。
- **解密子密钥顺序**：加密为 `K1 → K2`，解密必须反转为 `K2 → K1`。

## 3. 编码适配层：`sdes/codec.py`

### 3.1 分组与补位模式

| 常量 | 值 | 语义 |
| --- | --- | --- |
| `MODE_PAD` | `"pad"` | 最后一个不足 8 bit 的分组用 0 补齐；调用方需自行记录原始长度 |

### 3.2 API 一览

**位串 ↔ 字节/文本**

| 函数 | 说明 |
| --- | --- |
| `bytes_to_bits(data: bytes) -> str` | 每字节展开成 8 个字符 |

| `split_blocks(bits, size=BLOCK_BITS) -> list` | 按 size 切块 |
| `join_blocks(blocks) -> str` | 合并（与 `split_blocks` 互逆） |

**hex 辅助**

| 函数 | 说明 |
| --- | --- |
| `hex_to_bits(hexstr, width=0) -> str` | hex → 位串，`width>0` 时左侧补零到该宽度 |
| `bits_to_hex(bits) -> str` | 位串 → 大写 hex |

**字符串加解密（按 1 Byte 分组）**

| 函数 | 说明 |
| --- | --- |
| `encrypt_bytes(data, key) -> bytes` | 字节流加密 |
| `decrypt_bytes(data, key) -> bytes` | 字节流解密 |
| `encrypt_text(text, key, encoding="utf-8") -> str` | 文本 → 密文位串 |
| `decrypt_text(bits, key, encoding="utf-8", errors="strict") -> str` | 密文位串 → 文本 |

`key` 参数统一接受 **10 位 0/1 字符串**；密文 hex 长度 = 明文字节数 × 2（每字节加密成 8 bit = 2 个 hex 字符）。

## 4. 分析与攻击层：`sdes/crack.py`

### 4.1 常量

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `_KEY_SPACE` | `1 << KEY_BITS` = 1024 | 密钥总数 |
| `_BLOCK_SPACE` | `1 << 8` = 256 | 分组/密文总数 |

### 4.2 API 一览

| 函数 | 签名 | 说明 |
| --- | --- | --- |
| `brute_force` | `(pairs, *, want_all=True, progress=None) -> dict` | 单线程穷举；返回 `{"keys","tried","elapsed","rate"}` |
| `brute_force_threaded` | `(pairs, *, workers=4, chunk=64, want_all=True, progress=None) -> dict` | 多线程穷举，额外返回 `"workers"`、`"chunks"` |
| `brute_force_by_key` | `(key: str, plaintext: str) -> dict` | 演示：由已知密钥造出明密文对后再破解 |
| `equivalent_key_classes` | `() -> list` | 按 `(K1,K2)` 分组，返回规模 > 1 的组（本算法恒为空，见 4.3） |
| `analyze_collisions` | `(*, progress=None) -> dict` | 全空间枚举，返回 `table`/`per_plaintext`/`buckets`/`max_bucket`/`total_pairs`/`distinct_per_pt` |
| `collision_report` | `(sample_plaintext=0) -> str` | 生成中文文字版封闭测试报告 |

`progress` 回调签名统一为 `progress(tried: int, total: int)`；`brute_force` 每处理 256 个密钥回调一次。

### 4.3 两个必须区分的概念

| 概念 | 含义 | 本算法结论 |
| --- | --- | --- |
| **相同子密钥对** | 两个主密钥生成相同的 `(K1,K2)` | `equivalent_key_classes()` 实际按这一条件分组；配套材料记载其为空 |
| **全局等价密钥** | 两个密钥对**所有**明文都给出相同密文 | 需比较各密钥的完整 256 项输出向量，不能仅从上述函数的空结果推出 |
| **特定明文碰撞** | 对**某个给定明文**，多个密钥给出相同密文 | **大量存在**（最大桶 12 个密钥） |

**该函数的证据范围**：它遍历全部 1024 个主密钥，以 `key_schedule(k)` 返回的二元组为字典键，返回成员数大于 1 的组。空结果只能说明子密钥调度没有重复；不同子密钥对仍需通过完整加密行为比较才能判断是否全局等价。

**为什么必定存在特定明文碰撞**：固定 `P` 后，1024 个密钥映射到最多 256 个密文，由鸽巢原理至少存在多密钥同密文的桶。将不可达密文的空桶也计入时，平均桶大小为 1024/256=4；只统计可达密文时需使用 `1024 / distinct`。碰撞不代表每个密文桶都大于 1，也不保证任意两组明密文对都能唯一确定密钥。

### 4.4 `analyze_collisions()` 返回结构

```python
{
  "table":          {plaintext: {ciphertext: [key, ...]}},   # 全空间索引
  "per_plaintext":  {plaintext: {"max": int, "avg_keys_per_cipher": float, "distinct": int}},
  "buckets":        {桶大小: 桶个数},                        # 全局桶大小直方图
  "max_bucket":     int,                                    # 最大桶（本实现为 12）
  "total_pairs":    int,                                    # = 1024 × 256 = 262144
  "distinct_per_pt": float,                                 # 全部256个明文的平均不同密文数（材料记载为239）
}
```

### 4.5 多线程的真实效果（重要，勿误读）

算法层面提供 `brute_force_threaded` 是为了满足作业「你也可以考虑使用多线程的方式提升破解的效率」的扩展要求，但**在本算法规模下线程版本比单线程更慢**：

- 密钥空间只有 1024 个，单线程一次完整穷举约 **5 ms**；
- CPython 的 GIL 使纯 Python 的 `encrypt_int` 无法真正并行，多线程只增加分块与合并开销；
- 提交的性能截图记录：单线程 **4.885 ms**，`workers=1/2/4/8/16` 分别为 **5.395 / 5.663 / 6.228 / 5.990 / 6.236 ms**；这些是该次 15 次重复取中位数的结果，其他环境需重新测量。

结论：线程版本的价值在于**结果与单线程完全一致**（测试覆盖 `workers=1/2/4/16`），可作为教学对比；若要真正的并行加速，应改用 `multiprocessing` 而非线程。

### 4.6 扩展密钥空间：`sdes/longkey.py`

**动机**：10 bit 密钥空间只有 1024，穷举为毫秒级，不易展示实时过程。该模块把本仓库的作业版 S-DES 级联来扩大搜索空间，每层仍调用 `core.encrypt_int`，用于附加的视频演示。扩展实验的耗时和唯一性结论应与基础 10 bit 算法分开记录。

**构造**：主密钥 `K` 为 `L` bit，层数 `n = ceil(L/10)`，第 `i` 层子密钥取

```
子密钥_i = rotl(K, 10*i) 的高 10 位        (i = 0 .. n-1)
加密:  C = E_{s_{n-1}}( ... E_{s_1}( E_{s_0}(P) ) ... )
```

`L=10` 时 `n=1`、`子密钥_0 = K`，退化为本仓库作业版单层 S-DES。配套测试中有 1024×5 组与 `core` 的比对断言。

**常量**

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `MIN_KEY_BITS` | 10 | 下界（本仓库作业版单层 S-DES） |
| `MAX_KEY_BITS` | 40 | 上界（4 层，搜索空间为 `2^40`；耗时应按本机测速估算） |
| `DEFAULT_KEY_BITS` | 22 | 默认档位（3 层，可用于展示较长的搜索过程；耗时随机器而变） |

**API 一览**

| 函数 | 签名 | 说明 |
| --- | --- | --- |
| `subkey_count` | `(key_bits: int) -> int` | 层数 `ceil(L/10)` |
| `keyspace_size` | `(key_bits: int) -> int` | 密钥空间 `1 << L` |
| `subkeys_from_key` | `(key_int: int, key_bits: int) -> tuple` | 整数旋转实现推导层密钥 |
| `subkeys_from_string` | `(key_str: str) -> tuple` | 字符串切片实现（独立第二实现，用于互证） |
| `encrypt_ext` / `decrypt_ext` | `(plain/cipher: int, key_int: int, key_bits: int) -> int` | 第一个参数分别为 `plain`、`cipher`，整数分组加解密 |
| `encrypt_ext_bits` / `decrypt_ext_bits` | `(plain_bits/cipher_bits: str, key_int: int, key_bits: int) -> str` | 第一个参数分别为 `plain_bits`、`cipher_bits`，主密钥为整数 |
| `make_pairs` | `(key_int: int, key_bits: int, count=None, rng=None) -> list` | 随机生成不同明文的自洽明密文对；默认对数由密钥长度确定 |
| `crack` | `(pairs, key_bits, *, want_all=True, start_key=0, stop_key=None, interval=2.0, progress=None, max_seconds=None) -> dict` | 单线程穷举 |
| `crack_parallel` | `(pairs, key_bits, *, workers=4, interval=2.0, progress=None, max_seconds=None) -> dict` | `ProcessPoolExecutor` 版，受限环境发生 `OSError` 时回退单线程 |
| `crack_subprocess` | `(pairs, key_bits, *, workers=4, interval=2.0, progress=None, max_seconds=None, slice_size=65536) -> dict` | **实际使用的并行实现**：`subprocess` + 文件传结果，见下 |
| `measure_rate` | `(key_bits: int, samples: int = 20000, seed: int = 20261008) -> float` | 指定密钥长度的级联测速，候选/秒；单层基准用 `key_bits=10` |
| `estimate_seconds` | `(key_bits: int, rate_per_stage=None) -> float` | `2^L / (rate_per_stage / n)` |
| `suggest_bits` | `(target_seconds: float, rate_per_stage=None) -> tuple[int, float]` | 返回推荐密钥位数与预计秒数 |

**耗时模型（易错点）**：`rate_per_stage` 是**单层**每秒的候选数，与层数无关；
每试一个主密钥要跑 `n` 层，所以有效速率是 `rate_per_stage / n`。
早期实现漏掉这一项，导致 `est(20)/est(10)` 算成 1024 而非 2048，已修正。

**并行 — 为什么保留了两个实现**：

1. 常规启用 GIL 的 CPython 对纯 Python 计算不能以线程实现真正并行；[图 8 的说明](截图说明.md)记录线程版本比单线程略慢，
   故走进程路线。
2. 配套开发记录中的受限运行环境曾使常规进程路线（`multiprocessing` / `ProcessPoolExecutor`）失败：
   `PermissionError: [WinError 5]`。探针定位到根因是**沙箱禁止创建命名管道**——
   `Process+Queue`、`Pool.map` 全挂，但不传结果的**裸 `Process` 能起来**。
   `crack_parallel` 保留为另一种实现；该限制与平台和运行权限有关，不能推广为读者机器的固定行为。
3. `crack_subprocess` 绕开管道：每个子进程跑 `[0, total)` 的一段连续区间，
   把进度与结果**覆盖写进自己的 `out_*.json`**，父进程轮询各文件求和。
   具体速率以当次输出为准。提交的 24 bit 截图为限时 10.1 秒的部分扫描，不能作为完成全部空间的证据。

**`crack_subprocess` 的四个实现要点**：

| 要点 | 不这么做会怎样 |
| --- | --- |
| 进程数 = `workers`，每进程**一段连续区间** | 按「小块」起进程 → 4 进程 × 16 块 = 启动 16 个解释器，启动开销吃光加速比 |
| 临时目录用 `os.makedirs` 建在项目内 | 子进程与父进程需能写入 `_crack_*/`；这是当前实现的路径选择，历史沙箱权限问题不代表所有机器的系统临时目录都不可写 |
| worker 写 `tried` 时用**段内偏移** `tried - start` | 写绝对下标 → 父进程求和后进度会超过 100%（实测打印出 `250.0%`） |
| **先读结果再删临时目录** | 先 `rmtree` → 结果全空（`keys=[] tried=0`） |

另外 worker 的 `tried` 是「本段内已完成条数」，父进程求和时用
`min(tried, share)` 夹一次，避免 `--max-seconds` 中止时把未完成份额算进去。

**失败检测的范围**：启动与轮询过程中进入 `try` 的异常会回退单线程，但创建临时目录和写 `_worker.py` 在 `try` 之前，失败时可能直接抛异常。父进程目前用 `poll()` 判断是否结束，没有统一拒绝子进程的非零退出码；无法读取结果文件时会跳过该份额。因此进程结束或 `aborted=False` 都不能单独证明全空间完成，使用者应核对 `tried == span`、候选数量和当次日志。

**候选与等价行为**：配套材料记载 `L=12` 时 4096 个主密钥对应 4095 个不同加密函数。若两把主密钥对全部 256 个明文行为相同，增加明密文对也不能区分它们；应区别于只对当前样例成立的局部碰撞。不能将这种级联等价行为直接称作 DES weak keys。

## 5. TCP 通信：`sdes/server.py` + `sdes/client.py`

### 5.1 职责划分

```
明文 ──[客户端加密]──> 密文 ──TCP──> [服务端解密] ──> 明文回显
```

客户端本地加密后以 `DEC <hex>` 请求发送密文，服务端应答却是解出的明文；`KEY` 返回演示密钥，`ENC` 请求也可以直接传入明文。协议无认证或 TLS，因此只证明课程演示中的密文发送与解密功能，不能称为全会话不传明文。

### 5.2 行文本协议

- 编码 UTF-8，**一条命令一行**，以 `\n` 结束；
- 明文/密文中的换行与反斜杠由 `_escape()` 折叠成字面量（`\` → `\\`，`\r` → `\r`，`\n` → `\n`），接收侧用 `_unescape()` 还原，因此行协议不会被嵌入换行打断。

| 请求 | 应答 |
| --- | --- |
| `PING` | `PONG` |
| `KEY` | 当前服务端 10-bit 密钥 |
| `ENC <明文>` | 密文 hex（命令后的**全部内容**都是载荷，明文可含空格） |
| `ENC <密钥> <明文>` | 用临时密钥加密后的密文 hex |
| `DEC <密文16进制>` | 明文（换行已转义） |
| `DEC <密钥> <密文16进制>` | 用临时密钥解密后的明文 |
| `QUIT` | `BYE`，随后关闭连接 |
| 其他 / 出错 | `ERR <原因>`，**连接保持不断开** |

`ThreadingTCPServer` + `daemon_threads`，每个连接一个线程，支持多客户端并发；`allow_reuse_address = True` 便于快速重启。

### 5.3 密钥形式判定

`_parse_payload(rest, default_key)` 的规则：

1. 去除 `rest` 的首尾空白，然后按第一个普通空格分为 `first` 与 `remainder`；
2. **仅当** `remainder` 非空**且** `first` 是合法的 10 位 0/1 串（`_is_key`）时，才按 `ENC <密钥> <明文>` 解析；
3. 否则整个 `rest` 作为载荷，使用默认密钥。

> ⚠️ **已知歧义**：若明文本身恰好以「10 个 0/1 字符 + 空格」开头，会被误判为显式密钥形式。此时请显式写出密钥（`ENC <密钥> <明文>`），或改用 GUI 本地加解密。

### 5.4 默认参数

| 常量 | 值 |
| --- | --- |
| `DEFAULT_HOST` | `"127.0.0.1"` |
| `DEFAULT_PORT` | `50007` |
| `DEFAULT_KEY` | `"1010000010"` |

### 5.5 客户端类 `SDesClient`

```python
SDesClient(host=DEFAULT_HOST, port=DEFAULT_PORT, key=DEFAULT_KEY, timeout=5.0)
```

| 方法 | 说明 |
| --- | --- |
| `connect()` / `close()` | 建立/关闭连接；亦支持 `with SDesClient(...) as cli:` |
| `ping()` / `server_key()` | 连通性检查 / 读取服务端密钥 |
| `encrypt(plaintext, key=None) -> str` | 返回密文 hex；非法密钥在本地抛 `ValueError` |
| `decrypt(ciphertext_hex, key=None) -> str` | 返回明文；收到 `ERR` 前缀抛 `ValueError` |
| `send_message(message, verbose=True) -> dict` | 完整往返，返回 `{"plaintext","ciphertext_hex","server_plaintext","ok"}` |

命令行为 `python -m sdes.client`（默认跑 4 条演示消息）、`-m "文本"`（发一条）、`-i` / `--interactive`（交互）。支持 `--host`、`--port`、`--key`；`-m` 与 `-i` 同时出现时优先单条消息分支并退出。
CLI 与网页调用 `SDesClient.decrypt` 还原服务端转义后的应答；桌面版 `send_tcp` 直接读回包，只并列展示回显与本地解密结果，未调用 `_unescape` 或自动比较。

## 6. 网页版：`sdes/webapp.py` + `sdes/web/`

### 6.1 为什么选标准库 `http.server`

作业要求「自己设计 UI」，同时又受「零第三方依赖、开箱即跑」的约束（整个项目不装任何 pip 包，这也是第 2 关交叉测试能在任意机器上复现的前提）。因此没有引入 Flask/Vue 之类的框架，而是：

- **后端**：`http.server.ThreadingHTTPServer` + `BaseHTTPRequestHandler`，路由用两张字典表手工分发；
- **前端**：手写 HTML/CSS/ES6，无构建步骤、无 npm；必须通过启动的 HTTP 服务访问，直接双击 HTML 不提供后端 API；
- **通信**：`fetch` + JSON，统一响应包 `{"ok": bool, "data": ..., "error": str}`。

后端默认监听 `127.0.0.1:8000`，支持 `--host` 与 `--port`；加解密在 Python 后端完成。浏览器将明文与密钥作为 JSON 请求发送给该后端，第 3 关 TCP 的主机由页面参数指定。

### 6.2 常量与目录

```python
DEFAULT_HOST = "127.0.0.1"
DEFAULT_PORT = 8000
DEFAULT_KEY  = "1010000010"
DEFAULT_PT   = "10010111"
VECTOR_SEED  = 20261008          # 与gen_vectors同序列；桌面随机向量的取样顺序不同
_WEB_DIR     = Path(__file__).resolve().parent / "web"
```

`sdes/web/` 下的三个静态文件：`index.html`（6 个页签的骨架）、`style.css`（主题变量 + 打印样式）、`app.js`（全部交互逻辑）。

### 6.3 路由表

```python
_GET_ROUTES  = {"/api/meta": api_meta, "/api/report": api_report}
_POST_ROUTES = {
    "/api/encrypt":         api_encrypt,
    "/api/decrypt":         api_decrypt,
    "/api/text/encrypt":    api_text_encrypt,
    "/api/text/decrypt":    api_text_decrypt,
    "/api/vectors":         api_vectors,
    "/api/vectors/compare": api_vectors_compare,
    "/api/crack":           api_crack,
    "/api/collisions":      api_collisions,
    "/api/tcp/send":        api_tcp_send,
}
```

> 前端 `api(path, payload)` 在 `payload === undefined` 时走 GET、否则走 POST，与上表一一对应；
> `/api/meta` 与 `/api/report` 是**只读且无参数**的，所以注册在 GET 表里。

### 6.4 API 一览

| 接口 | 入参 | 返回要点 |
| --- | --- | --- |
| `POST /api/encrypt` | `plaintext`, `key` | `ciphertext`, `ciphertext_hex`, `k1`, `k2`, `steps`（逐步跟踪中间量） |
| `POST /api/decrypt` | `ciphertext`, `key` | `plaintext`, `plaintext_hex`, `k1`, `k2` |
| `POST /api/text/encrypt` | `text`, `key`, `encoding` | `ciphertext_hex`, `byte_count`, `block_count`, `padded_bits`, `plaintext_bits` |
| `POST /api/text/decrypt` | `hex`, `key`, `encoding` | `hex`, `text`, `key`, `encoding` |
| `POST /api/vectors` | `count`（1~5000）, `key`(可选) | `rows`（`pt,key,ct`）, `csv`, `seed` |
| `POST /api/vectors/compare` | `csv_a`, `csv_b`（CSV 文本） | `same`, `same_set`, `local_rows`, `remote_rows`, `total`, `mismatch_count`, 前 20 条位置差异 `mismatches` |
| `POST /api/crack` | `pairs`（`[[明文,密文], ...]`）, `workers`, `chunk`, `threaded` | `keys`（10-bit 串）, `key_count`, `tried`, `elapsed_ms`, `rate`, `workers`, `chunks`, `threaded`, `pair_count` |
| `POST /api/collisions` | `sample`（0~255） | `key_space`/`block_space`/`total_pairs`/`max_bucket`/`distinct_per_pt`/`avg_candidates_per_cipher`/`buckets`/`equivalent_classes`/`sample`；样例固定最多 8 条，无 `limit` 参数 |
| `POST /api/tcp/send` | `text`, `key`, `host`, `port` | `log`（分步日志）, `ciphertext_hex`, `server_plaintext`, `server_key`, `ok` |
| `GET /api/meta` | — | 版本、默认值、全部规格表、SBox2 提示 |
| `GET /api/report` | — | 与 `crack.collision_report(0)` 完全一致的文字报告 |

这些函数具有 `payload: dict -> dict` 接口，可脱离 HTTP 调用，但并非全部是纯函数：`api_tcp_send` 建立真实 TCP 连接，`api_crack` 可创建线程池，全空间分析也执行耗时枚举。

`encoding` 可选，字符串加解密默认 UTF-8；TCP 发送固定 UTF-8，当前前端不会将编码下拉框的值传给 `/api/tcp/send`。
位串 API 的 `_bits` 会去空白和下划线；文本在编码后按完整字节分组，`padded_bits` 为 0。字符串加解密不走 `encrypt_bits_partial` 的补零模式。

### 6.5 错误映射

`SDesWebHandler._invoke` 把异常统一翻译成 HTTP 状态码，前端只看 `error` 字段：

| 异常 | 状态码 | 说明 |
| --- | --- | --- |
| `ValueError` | 400 | 参数校验失败（位数、字符集、条数越界等） |
| `ConnectionRefusedError` | 502 | TCP 服务端未启动，提示先跑 `python -m sdes.server` |
| `OSError` | 502 | 其它网络错误 |
| 其它 `Exception` | 500 | 兜底 |

静态文件由 `_serve_static` 处理：`Path.resolve()` 后检查是否仍在 `_WEB_DIR` 之下，`/../sdes/core.py` 这类目录穿越会返回 403。

### 6.6 前端结构（`sdes/web/app.js`）

单个 IIFE、严格模式，无框架：

- 公共工具：`api(path, payload)`、`cleanBits`、`setStatus`、`withBusy`、`showError`、`escapeHtml`、`table`、`download`、`copyText`、`setProgress`；
- 每个页签一个 `initLevelN()`，在 `DOMContentLoaded` 时统一初始化，第 4 关会预填一组自洽的明密文对；
- 按钮触发的计算与通信使用 `withBusy`，请求期间禁用该按钮并切换状态灯；启动时读取 `/api/meta` 的请求不经过这个包装。

### 6.7 一致性保证

网页版被 `tests/test_webapp.py` 的 148 项断言覆盖，核心思路是**用 HTTP 接口的结果去比对直接调用内核的结果**：

- 单分组加解密必须等于 `core.encrypt`；`k1`/`k2` 必须等于 `core.key_schedule`；
- 字符串加密必须等于 `codec.encrypt_text_hex`；
- 暴力破解候选集必须等于 `crack.brute_force` / `brute_force_threaded`；
- 碰撞统计必须满足 `sum(size * count) == total_pairs`（注意 `buckets` 是「桶大小 → 该大小的桶个数」直方图，不是密钥计数表）；
- 网页版生成 CSV 与自己比对必然 `same=True`，篡改一行必然 `same=False`。

因此「网页版改坏了内核」或「前端与后端理解不一致」这类问题会在自测阶段就被抓住。

python -m tests.test_longkey       # 第4关进阶: 扩展密钥空间

### 8.1 第 2 关交叉测试工具 `tests/cross_test.py`

仓库不附带搭档源码，也不含默认 `_组2参考/SDES/sdes` 目录。复现时必须自行提供兼容的独立实现并用 `--other` 指定目录；缺少实现时脚本会提示找不到目录。生成记录可再加 `--md "docs/交叉测试记录.md"`，该输出文件需运行后才存在。

**问题**：作业 3.2 要求"两人一组、相同算法流程与转换单元"，但两份实现的代码形态几乎必然不同，
无法直接 `import` 后调用同一个函数。

**做法**：把对方的 `sdes` 包当作**外部模块**加载进一个独立的命名空间，中间加一层适配器。

```python
spec = importlib.util.spec_from_file_location("group2_core", other_dir / "core.py")
# 以独立模块名注册，避免污染/覆盖本项目的 sdes 包
```

适配器解决三类差异：

| 差异 | 本项目 | 对方（第二组） | 适配方式 |
| --- | --- | --- | --- |
| 位表示 | `str`（`"1010"`） | `list[int]`（`[1,0,1,0]`） | 双向转换函数 |
| 属性命名 | `SBOX1` / `SBOX2` / `SPBOX` | `S_BOX_1` / `S_BOX_2` / `P4` | `_TABLE_ALIASES` 逐个候选名回退 |
| 字符串编码 | UTF-8 | latin-1 | 比对只用逐字节 hex，不比较文本编码 |

**五项验证**（对应作业 3.2 的两个分支）：

| 编号 | 验证 | 说明 |
| --- | --- | --- |
| [1] | 转换单元逐项比对 | 8 张表（含 S 盒）必须完全相同——这是"统一转换单元"的前提 |
| [2] | 密钥扩展 (K1, K2) | 1024 个主密钥全比对，可定位 `key_schedule` 的差异 |
| [3] | 方式① 加密一致 | 同一 (明文, 密钥) 双方各自加密，比密文 |
| [4] | 方式② 对方加密→我方解密 | 跨实现解密互操作 |
| [5] | 方式② 反向 我方加密→对方解密 | 双向都要过，避免只有单向巧合一致 |

**实现要点**

- 展示前 12 行（便于截图）用的是「5 条标准向量 + 全空间前若干条」的**去重集合**；
  统计时 `full=True` **只**取全空间 262144 组，避免 5 条标准向量被重复计入而出现 262149 这种怪数。
- 展示行的比对结果**必须计入** `mismatch` 统计，否则屏幕上看着有差异、总结论却写"全通过"。
- `--md` 导出的 Markdown 用 UTF-8 无 BOM 写入，可直接贴进测试报告。

## 9. `sdes/__init__.py` 的惰性重导出（PEP 562）

包根采用模块级 `__getattr__` 实现惰性重导出，而不是在导入包时立即 `from .core import *`。原因：立即导入会让 `python -m sdes.core` 触发

```
RuntimeWarning: 'sdes.core' found in sys.modules after import of package 'sdes',
but prior to execution of 'sdes.core'
```

惰性实现保留了两种用法：

```python
import sdes
sdes.encrypt("10010111", "1010000010")      # 属性式访问（首次访问时按需导入）
from sdes import core, codec, crack, gui    # 子模块式导入
sdes.MODE_PAD                               # codec 中的常量
```

`_LAZY` 字典描述「子模块 → 对外符号」，`_OWNER` 是它的反查表，`__dir__()` 会同时列出全局变量与全部惰性符号。未定义的名字访问会抛标准 `AttributeError`。

## 10. 代码规范

- **命名**：变量、函数、类均使用描述性名称；函数与变量用 `snake_case`，类用 `CamelCase`；仅循环下标等临时量使用单字符。
- **注释**：使用清晰、有意义的中文说明「做什么、为什么」，不复述代码字面；对置换表、位序约定、协议歧义等易错处必须注释。
- **函数式/模块化**：每个函数只承担一件事（如 `_permute` 只做置换），通过组合复用；公开 API 与内部工具以 `_` 前缀区分。
- **零第三方依赖**：仅使用标准库，保证在不同机器上「开箱即跑」，这也是第 2 关交叉测试能顺利比对的前提。

## 12. 常见坑位速查

| 现象 | 原因 / 处理 |
| --- | --- |
| `ModuleNotFoundError: No module named 'sdes'` | 不在项目根目录运行；`python -m 包名.模块名` 必须以根目录为工作目录 |
| 与网上标准 S-DES 测试向量不符 | **预期行为**，本作业 SBox2 已被改写 |
| `'sdes.core' found in sys.modules ... RuntimeWarning` | 已由 `sdes/__init__.py` 的惰性重导出修复；若自行改回立即导入会复现 |
| 多线程破解没有变快 | 算法规模太小 + GIL，见 4.5；这是结论而非缺陷 |
| `ENC <10位0/1> ...` 被当成密钥 | `_parse_payload` 的已知歧义，见 5.3，显式写密钥即可规避 |
| 网页版 404 / 目录穿越被拒 | 静态文件只在 `sdes/web/` 下查找，`_serve_static` 会 `resolve()` 后做前缀校验，返回 403 属正常防护 |
| 网页版点按钮没反应 | 打开浏览器开发者工具的 Console 看 `fetch` 报错；若 `error` 里含 `sdes.server`，就是 TCP 服务端没启动 |
| 网页版端口被占用 | `OSError` 由 `main()` 捕获并提示换端口，重跑 `python -m sdes.webapp --port 8080` |
| 控制台中文乱码 | 设置 `$env:PYTHONIOENCODING="utf-8"`（PowerShell）或 `chcp 65001` |
| 扩展密钥空间里候选密钥是 2 个而不是 1 个 | 当前明密文对可能未区分两把密钥；局部碰撞可增加不同明文样例，全局等价行为则不能这样区分，见 4.6 |
| `sdes.longkey --workers N` 提示回退单线程 | 某些运行环境限制子进程或文件访问；进入回退分支时输出原因。临时目录创建失败与子进程异常结束未必触发回退，详见 4.6 |
| 第 1 关解密后 8-bit 框显示的和 hex 对不上 | 历史缺陷（已修）：加密响应把结果放在 `ciphertext`/`ciphertext_hex`，解密放在 `plaintext`/`plaintext_hex`，`fill()` 曾统一按密文字段取，于是解密时 8-bit 框显示的是**输入框里的值**。现由 `fill(result, decrypting)` 按方向取字段，标题也随方向切换。改这两个函数的调用方时要同步传 `decrypting` |
| 并行破解进度百分比超过 100% | 历史缺陷（已修）：worker 曾上报**绝对下标**，父进程对 N 段求和即放大 N 倍。现在 worker 写**段内偏移** `tried - start`，见 4.6 |
